## 1. 固定方向

- C# 是主引擎和唯一游戏逻辑语言，拥有 World、组件、调度、场景/资产元数据、编辑业务及唯一事务/Undo。
- 新目标：C# ECS 是唯一运行时数据存储；GameObject 是同一 Entity 的高级封装，不复制组件状态、不建立双运行时同步。源码已采用强类型池和代次 Entity，仅保留 Ncma.GameObject 高层门面；低层 Runtime.GameObject 及旧 API 已迁移删除，没有兼容壳；完整 ECS 和性能验收尚未完成。
- 新增规划：创作数据与运行数据分域，通过受检构建/烘焙边界转换；统一声明生成元数据及受检访问代码；任务显式声明组件与外部资源读写依赖。三项按 E6-A/B/C 交付，不代表当前已支持独立运行模型或多线程 ECS。
- C++ 是性能插件与原生表现层：渲染、物理、经测量需要的动画/导入/数学内核及现有 Dear ImGui。旧 C++ Editor/World/CLR 桥已删除。
- Python 是可选异步专长模块，不挂 Behaviour，不拥有 live World。M8.2 gRPC 工具 worker 已有候选代码；pythonnet、ZeroMQ、模型推理未实现。
- 场景采用扁平 GameObject 列表、空容器 + 组件，Transform 可选；不恢复 Node、Actor 复制、对象父子树或变换继承。
- AI 深度参与场景、资产、动画、UI、工具和托管扩展，但与人工共用领域命令、授权、预检、事务与 Undo；不提供通用执行后门。
- 一个共享渲染框架，两条独立产品管线：2D 足够轻，3D 默认可用、简单定制。纯 2D 不强制初始化/部署 3D 资源。
- 本版本只交付 DX11；Vulkan/OpenGL 保留契约扩展，下版本实现。不继续承诺 DX12。
- M9 先实现 Windows 正式导出；微信小游戏、Android、iOS 仅保留平台扩展目标，后续版本实施。
- 网络保持独立可选服务，不与 GameObject/组件耦合。模块 gRPC 不等于多人游戏网络。
- 保留用户图片确定的统一编辑器风格；移除类 Figma 参考，不改变独立 UI 制作/HUD 目标。

#### E6-A：编辑模型与运行模型分离

- 编辑模型面向制作：持久 UUID、可编辑组件描述、脚本绑定、资产引用、版本与唯一 EditSession/Undo；选中状态等编辑临时数据不进入运行组件热路径。扁平对象组织和可选 Transform 保持。
- 运行模型面向执行：每个运行会话只有一份权威 ECS 状态；GameObject 仅为同一 Entity 的高层门面。Player 的模拟路径不依赖编辑文档、Undo 或属性面板，也不逐帧往返完整文档/JSON。
- 显式转换边界：校验并归一化已提交编辑版本，解析资源/脚本依赖，生成版本化运行数据及 UUID 映射；加载时才建立 World/Index/Generation 身份。运行句柄不得持久化或作为 AI 提案身份。
- Play 使用隔离运行状态。运行时销毁、移动和脚本状态不得自动污染编辑文档；Stop 默认丢弃运行变更。保留运行改动或编辑期热应用必须走显式 diff、revision/权限检查及原唯一事务/Undo，不做后台双向镜像同步。
- 检查器/AI 读取运行态时使用标明会话、代次与时点的有界只读快照。Editor 预览复用运行能力，但不建立另一份持续同步的权威组件存储。
- 验收包含：相同输入的确定性产物、对象/资产引用映射、纯 2D 不携带 3D 依赖、Play/Stop/Reload 隔离、陈旧句柄拒绝、转换失败不替换有效运行状态、共享事务 Undo/Redo 与无窗口/图形 Player 联合测试。M9 复用该转换链，不另造发布专用模型。

#### E6-B：元数据与访问代码生成

- 以 C# 类型及显式声明为单一来源，规划构建期增量生成器；稳定 TypeId/FieldId、schema 版本、默认值、可编辑/持久化/运行属性与访问能力有明确合同，不以类型名或程序集加载顺序代替持久身份。
- 生成组件注册、字段描述、强类型读取/受检写入和常用查询访问代码，供 Inspector、序列化适配、AI/MCP schema 和后续任务调度共用。生成元数据不直接授予写权限；AI 仍通过授权领域命令和唯一历史。
- 热路径避免逐字段反射、字符串查找和逐实体装箱；生成器不能给出裸池指针或可跨 tick/await 的不受限 ref，仍执行 World 身份、代次、写作用域、预算、结构命令及脏写集规则。
- 重复标识、不支持类型、非法持久引用、无效访问声明和生成依赖冲突必须产生定位到源码的诊断。类型/schema 变更采用明确版本与迁移计划，不恢复已删除的旧格式、旧类型兼容壳。
- 验收包含：干净与增量构建生成结果可重现，修改声明能正确失效，陈旧生成物不能静默使用；负例诊断、编辑/运行/MCP 描述一致、实际生成 API 与现有语义等价；通过测量确认启动/热循环分配与时间成本，不把“有生成代码”当作性能通过。

#### E6-C：声明读写依赖的任务调度

- System/任务声明组件 `Read<T>` / `Write<T>`、结构变更和输入、信号、资源、物理、渲染等外部状态的访问集合，同时声明阶段、明确前后依赖和线程归属；不能只描述组件而遗漏外部副作用。
- 保守构建依赖图：读/读允许独立，读/写和写/写建立确定性冲突边；显式依赖环和未声明访问拒绝。任务身份及合并顺序稳定，不依赖线程完成顺序；同类型不同实体的并行仅在能证明范围互斥时开放。
- 先交付可检查的串行任务图，再启用有界工作线程。初期只并行化声明完整的纯计算/受检数据任务；Behaviour、编辑事务和具有线程要求的原生插件保留相应 owner-thread 阶段，不将任意 `Task.Run` 或共享 World 写入当作调度实现。
- 保持读已提交状态、暂存写集及唯一发布点。依赖边不隐式发布上游组件写入；确需中间结果时使用声明过的不可变任务输出。结构命令、跨任务冲突和回执按既有规则统一预检/确定性合并，失败不得发布部分结果；物理执行后的故障仍 fail-stop，不能承诺外部副作用回滚。
- 任务数量、队列、临时缓冲、取消/故障收敛和生命周期受预算限制。Python/推理/IPC 仍异步回提案，不能成为固定步必须同步等待的任务。
- 提供只读任务图、访问集合、冲突原因和耗时诊断，供编辑器与 AI 分析；不开放运行中任意改图或权限提升。验收覆盖串行/多线程同输入最终状态与回执等价、顺序/环/漏报/结构变更负例、取消和异常、owner-thread 约束、小场景开销及真实领域吞吐/尾延迟。

E6 每片均须先审计消费者、明确新合同，再实现并准备对应测试用例；片间不运行测试、不以定向测试通过作为推进条件。替代消费者就绪后删除废弃入口，不保留兼容壳。E6-A/B/C 全部实现后，才对同一冻结候选统一执行各片定向测试、完整双配置验证和必要的固定性能对照，同时验证编辑创作 → 生成/转换 → Play/Player → AI 提案回到原事务的闭环；失败则修复并复测，未执行前一律标为待验证。当前 E5 的失败记录、性能债务、目标机/人工/长稳门禁及用户暂缓代表性内容的决定不因新增阶段被豁免。

### M8.3 领域提案闭环

前置：M8.2 已交付，ECS E0–E5 收尾及新增 E6-A/B/C 已按各自约定门禁验收；AI 领域提案以编辑模型、生成描述符和受检命令为入口，不直接修改运行组件存储。

- 将可选模块结果接回现有场景、动画、UI、资产领域服务；先覆盖已具备真实读写业务的操作。
- 请求绑定精确项目/会话/文档代次/revision/权限；返回有界结构化提案。
- 先做 schema/语义验证和 dry-run/diff，再由本地人类批准同一命令/事务。
- 资产写入与 Prefab 操作必须先补对应 M3 业务，不允许文本占位“成功”。
- 验收：有效提案单次提交/Undo/Redo，陈旧/撤权/换场景拒绝，失败不留部分修改；人工与 Agent 操作语义一致。

### M8.4 真实模型与正式 AI 工作区

- 由用户选择一个真实本地或远程模型服务，不同时铺开所有供应商/传输。

- 验收：真实模型在已批准范围完成一个场景/动画/UI 制作任务；超时、断连、取消与拒绝均可解释，不阻塞 tick。

### M8.5 托管扩展

- 使用可信启动注册的 C# 扩展契约、版本/依赖校验、明确生命周期与关闭规则。
- AI 可提出扩展方案或代码补丁；审查、编译/测试、安装/重启分别受控。
- 不开放任意程序集路径加载、eval、shell 或运行中私自提升权限。
- 验收：错误版本/依赖拒绝，重复注册与卸载顺序可测，资源先失效再释放；默认运行产品不受影响。

### M8.6 可审计开发工作流

- 串联观察、计划、精确审批、领域命令或已批准补丁、构建/测试、结果回执。
- 复用已有 workflow ledger，不把它扩张成第二个命令执行器/历史。
- 明确取消、部分成功、外部 IO 和代码变更不能随 World Undo 自动回滚；不得覆盖用户后续编辑。
- 验收：每步可追踪，失败可停止与受检恢复，无隐式安装/发布/Git 写入。

### M8.7 联合验收

- 默认无 Python 产品与显式启用模块产品分别验证；客户端/worker 独立搬移，缺件/改变包拒绝。

- 模块启动/故障/关闭、取消/背压、身份/权限撤销及资源泄漏联合测试。
- 测量端到端延迟、CPU/内存/分配与帧影响；测试驱动轮询耗时不能冒充纯 RPC 延迟。
- 完整 Debug/Release、实际客户端人工验证、长稳分别记账；未通过不标生产就绪。

## 7. 推进与验收规则

- 每个小阶段：明确范围 → 实现 → 定向测试 → 必要的完整双配置回归 → 记录剩余门禁 → 提交推送 → 下一片。
- 用户确认的新顺序覆盖旧“M8.2 后直接进入 M8.3”的安排；本轮计划更新不等于已开始重构。
- 一次只推进一个闭环，不并行扩张模型供应商、传输后端与新发布平台。
- ECS 方向已确认，但具体存储/提交优化仍以 E0 剖析和回归为依据；2D/3D 效率用 CPU/GPU/分配/上传/驻留数据验证，不预先承诺零拷贝或性能倍数。
